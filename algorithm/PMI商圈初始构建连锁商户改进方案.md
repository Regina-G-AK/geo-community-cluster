# PMI 商圈初始构建的连锁商户改进方案

## 背景

`商圈构建算法设计0613.md` 中的初始构建方案，核心链路是线上商户识别、交易对生成、PMI/SPPMI 建图、互为 top-k 稀疏化、迭代 hub 清洗、Leiden 社区发现和锚点确认。该方案默认图节点已经是可代表线下实体的商户。

目前的风险是：大量连锁门店使用同一个商户名称。如果图节点直接使用商户名称，同名门店会被错误合并成一个超级节点。此时 PMI 只能看到已经合并后的高频节点，无法再区分不同地点的真实门店，容易出现以下问题：

- 同一名称跨商圈的交易被汇总到同一个节点。
- 该节点会连接多个真实商圈，形成类似线上商户的桥接 hub。
- PMI 可能无法有效压低它，因为每个真实门店在本地都有真实共现，合并后会把多个局部强信号叠加。
- Leiden 会被同名节点粘连，导致多个商圈被错误合并。
- 锚点选择可能误把高客流连锁名称选为中心，降低商圈身份稳定性。

因此新方案不把连锁识别放在 PMI 之后补救，而是在 PMI 之前明确“节点只用商户 ID，名称只用于诊断”。PMI 继续作用于商户 ID 级节点，不再对同名组做额外权重调整。该方案不要求开发人员额外获取完整商户主数据，也不依赖地址、POI、终端号、城市等字段。

## 核心原则

1. **图节点必须是门店实体，不是商户名称。**
   - 输入数据只有 `merchant_id` 和 `merchant_name` 时，`merchant_id` 是唯一可用的门店级节点。
   - `merchant_name` 只能派生同名组，不能作为图节点。
   - 同名但不同 `merchant_id` 的商户必须保留为不同节点。

2. **PMI 不负责修复错误合并的节点。**
   - PMI 能压低“随机和很多人共现”的 hub。
   - PMI 不能把已经按名称合并的多个真实门店重新拆开。
   - 节点粒度错误必须在建图前修正。

3. **连锁商户不是一律剔除，而是商户 ID 级保留、同名组诊断。**
   - 本地门店仍然可能是商圈成员。
   - 同一名称的多商户 ID 只用于识别风险、解释结果和辅助复核。
   - 不因为商户同名就降低它的 PMI 边权，避免误伤真实本地门店。

## 改进后的整体流程

```plain
原始交易
  → 明确数据字段
  → 同名组派生
  → 商户 ID 级节点确定
  → 线上商户识别
  → 到访事件合并
  → 商户 ID 级交易对生成
  → 商户 ID 级 PMI/SPPMI
  → 互为 top-k 稀疏化
  → 迭代 hub 清洗
  → Leiden 社区发现
  → 连锁风险质量校验
  → 锚点候选生成
```

与原方案相比，新增的关键环节是：

- PMI 前新增“同名组派生与商户 ID 级节点确定”。
- PMI 计算仍使用原方案公式，但节点从名称改为 `merchant_id`。
- 同名组只用于质量校验和锚点风险提示。
- 质量校验新增连锁覆盖率、同名分散度和可疑社区指标。

## 一、明确数据字段

本方案明确商户身份侧只有两个字段：

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `merchant_id` | 商户 ID | 建图节点、追溯交易 |
| `merchant_name` | 商户名称 | 派生同名组、识别连锁风险 |

交易共现计算仍沿用原方案需要的持卡人和时间字段，例如持卡人 ID、交易时间等；这些属于交易事实字段，不属于商户主数据。

实现侧只允许派生一个内部字段：

```plain
name_key = normalize(merchant_name)
```

`name_key` 不是输入数据字段，只是程序运行时的同名分组 key。名称处理只做最小归一：

- 去掉首尾空格、连续空格。
- 统一全角半角、大小写和常见括号。
- 不解析品牌、分店、地址、商场名。
- 不基于名称做商户合并。

如果归一规则不确定，可以直接使用 `name_key = merchant_name`。这会少识别一些同名变体，但不会引入错误合并。

## 二、同名组风险识别

对每个 `name_key` 计算连锁风险特征。特征只使用 `merchant_id`、`merchant_name` 和交易共现中间结果：

| 特征 | 解释 | 连锁风险信号 |
| --- | --- | --- |
| 同名商户 ID 数 | 同一 `name_key` 下的 `merchant_id` 数量 | 数量越多越像连锁 |
| 客群重叠度 | 同名商户号之间的客户集合重叠 | 重叠越低越像不同门店 |
| 共现邻域差异 | 同名商户号各自 top 邻居集合的差异 | 差异越高越像不同地点 |
| 社区分散度 | 预建图后同名商户落入的社区数量 | 多社区分布说明不是单店 |
| 组内总边际量 | 同名组全部商户的边际共现量 | 越大越容易成为桥接组 |

同名候选输出三类结果：

- **普通同名组**：同名商户号少、客群和邻域高度重叠，不作为连锁重点处理。
- **高风险同名组**：同名商户号多、客群重叠低或邻域差异明显，需要进入质量校验和人工复核提醒。
- **疑似桥接同名组**：同名组边际量大，且边分散到多个社区，按桥接风险处理。

这里的判断不需要输出人工可解释的实体证据，也不要求给每个节点打置信度。它只回答一个问题：这个 `name_key` 是否提示存在同名多地点风险。该风险只进入诊断报告，不进入 PMI 和边权。

## 三、商户 ID 级节点确定

节点确定只有一条规则：

```plain
graph_node_id = merchant_id
```

禁止使用 `merchant_name` 作为节点。即使两个商户名称完全相同，只要 `merchant_id` 不同，就必须作为两个节点参与 PMI。这样至少能保证“同名多门店”不会在建图前被合并成一个超级节点。

## 四、商户 ID 级 PMI/SPPMI

PMI 的计算对象从商户名称调整为 `merchant_id`：

$$
C(i,j)=\sum_u s_u(i,j)
$$

其中 $i,j$ 是商户 ID 节点，不是名称。边际量也按商户 ID 计算：

$$
C(i)=\sum_{j\ne i} C(i,j), \qquad T=\sum_{i<j} C(i,j)
$$

PMI 为：

$$
\mathrm{PMI}_{id}(i,j)=\log \frac{C(i,j)\cdot T}{C(i)\cdot C(j)}
$$

再做 SPPMI：

$$
\mathrm{SPPMI}_{id}(i,j)=\max(\mathrm{PMI}_{id}(i,j)-\log k,\ 0)
$$

这里不加入同名组权重调整。原因是图节点已经是 `merchant_id`，同名门店不会在 PMI 前被合并；如果再按名称调整权重，会把真实位于本地商圈内的连锁门店一起压低，反而损失有效邻近信号。

## 五、互为 top-k 稀疏化

沿用原方案的互为 top-k 规则，不增加同名组约束：

1. 每个商户按 $\mathrm{SPPMI}_{id}$ 取 top-k 邻居。
2. 边 $(i,j)$ 保留当且仅当 $j$ 在 $i$ 的 top-k 中，且 $i$ 在 $j$ 的 top-k 中。
3. 后续 Leiden 使用该稀疏图。

同名组不参与边权排序，也不限制 top-k 占比。高客流连锁门店若确实跨社区连接，会被原方案的参与系数和迭代 hub 清洗识别；如果它只连接本地社区，就应当保留为正常商圈成员。

## 六、迭代 hub 清洗

原方案用参与系数 $P_i$ 清洗线上 hub：

$$
P_i = 1 - \sum_s \left(\frac{k_{is}}{k_i}\right)^2
$$

清洗规则沿用原方案：

- 单个门店 $P_i$ 高且度数高：按原方案识别为桥接节点，移除或降权后重跑 Leiden。
- 同名组只参与清洗后的统计诊断，不参与节点移除或边权调整。

这样可以避免因为“名称相同”误伤本地有效门店。真正粘连多个社区的是单个商户 ID 的图结构行为，而不是名称本身。

## 七、锚点选择的连锁提示

原方案锚点分为：

$$
\text{AnchorScore}(m)=c(m)\cdot(1-P_m)\cdot\text{stab}(m)\cdot(1+\lambda r(m))
$$

新方案不降低连锁商户的图权重，只在锚点候选中增加同名风险提示：

$$
\text{AnchorRisk}(m)=\mathbf{1}[N(m)\ \text{为高风险同名组}]
$$

其中 $N(m)$ 是商户 $m$ 的 `name_key`。

锚点选择规则同步调整：

- 高风险同名组商户可以进入候选，但需要在人工确认时标记风险。
- 同一商圈内同一 `name_key` 的锚点数量应设上限。
- 锚点集合必须包含非连锁或低同名风险商户，避免商圈身份被单一名称绑定。

连锁门店的价值更适合用于质量校验：如果同一名称的多个商户 ID 把多个社区连成一片，则说明建图仍有粘连风险。

## 八、质量校验

每次初始构建实验除保留原方案统计外，新增连锁商户专项统计：

| 指标 | 含义 |
| --- | --- |
| 同名组总数 | `name_key` 数量 |
| 高风险同名组数 | 被识别为连锁风险的同名组数量 |
| 连锁风险商户数 | 高风险同名组下的 `merchant_id` 数量 |
| 最大同名商户数 | 单个 `name_key` 下最多 `merchant_id` 数量 |
| 连锁相关原始边数 | 至少一端为连锁门店的边数 |
| 连锁相关 SPPMI 保留边数 | PMI 后仍保留的连锁边数 |
| 高风险同名组边数 | 至少一端属于高风险同名组的保留边数 |
| 高风险同名组跨社区边数 | 高风险同名组在社区之间形成的保留边数 |
| 可疑社区数 | 连锁占比过高或同一名称跨社区粘连的社区数 |

自动分析必须新增以下结论：

- 连锁边在最小支持度、SPPMI、互为 top-k、迭代清洗各阶段的保留率。
- 商户损失最大的阶段是否集中发生在高风险同名组。
- Top 同名组是否覆盖多个社区。
- 是否存在单一 `name_key` 占比过高的社区。
- 是否存在同一 `name_key` 下商户 ID 跨社区粘连的迹象。

## 总结

原 PMI 方案的问题不在于 PMI 公式本身，而在于图节点可能被错误定义为“商户名称”。当多个真实门店共享同一名称时，PMI 面对的是已经合并后的超级节点，无法再恢复地点差异。

改进方案的关键是把“名称”从图节点中剥离出来：

- `merchant_id` 负责表达商户 ID 级节点。
- `name_key` 由 `merchant_name` 派生，只负责表达同名组。
- PMI 只在 `merchant_id` 节点上计算。
- 同名组信息只用于识别、统计、复核提示和质量校验。
